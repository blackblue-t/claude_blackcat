# 前端改動檢查卡（/grill-ui）

給「改個畫面」等級的小任務用——完整 `/grill` 太重,零思考又危險。
`/grill` 的輕量分支:同一套訪談機制,換成前端專用的題目卡。

## 機制（與 /grill 同源）

- **能自答的不問人**:每一項先嘗試從 codebase、DESIGN.md、IA.md、
  既有元件用法查證出答案——查得到就記下結論,不打擾使用者。
- **真正的決策才問**,一次一題,**每題附你的建議答案**讓使用者
  可以只回「好」。通常整張卡問到使用者的不超過 2-3 題。
- 一項一項走,前一項的答案會改變後面的問法（例:第 1 項發現碰
  共用元件,第 2 項的狀態盤點就要對所有使用處問）。
- 全部項目有結論才動手。

## 檢查卡（逐項答:OK / 不適用 / 要處理）

1. **波及範圍**:動到哪些頁面/元件?**碰到共用元件嗎**——會不會改一處
   壞三頁?（共用元件要改,先列出所有使用處給使用者看）
2. **元件狀態**:hover / focus / disabled / empty / loading / error
   各是什麼樣?改動有沒有漏掉其中某態?
3. **RWD**:mobile / tablet / desktop 三檔都想過?**文字變長會不會
   爆版**（中文換英文、長 email、長人名）?
4. **深淺模式**:DESIGN.md 有深色模式的話,對應的深色值改了嗎?
5. **Tokens 合規**:有沒有偷渡 DESIGN.md 之外的色值/字級/間距?
   icon 是指定的那一套嗎?
6. **文案**:改了文字的話——有 i18n 檔要同步嗎?會不會弄紅測試?
   （行為斷言不該紅;紅了代表那條測試寫錯,標記給 review 清）
7. **a11y**:對比度夠嗎?鍵盤走得到嗎?需要 aria 嗎?
   （裝有 ui-ux-pro-max 就查它的檢查清單）
8. **測試**:行為有變才動測試;純視覺/文案不新增測試。

## 產出

不寫獨立文件。把「要處理」的項目直接列進本次的 worklog 條目
（`did:` 之下附一行 `ui-check: <要處理的項目>`），做完逐項銷。

## 使用時機

- `/go` 快車道判定是前端改動時**自動走這張卡**。
- 手動小改前也可以單獨跑：`/grill-ui 把價格卡改成三欄`。
- 發現任何一項答案是「這其實會動到邏輯/資料」→ 停,轉完整流程。
