# 文件拷問（/grill-doc）

用法：`/grill-doc docs/需求.md`（沒給路徑就問使用者要拷問哪份）。

`/grill` 是從零問出需求；本指令是**已經有一份文件**，把它問到能用，
並且**邊談邊改**——不是最後才產出一份新的。

## 開場（動筆前）

1. 讀完整份文件。跑 `git status`：
   - 檔案在 git 裡且乾淨 → 直接就地改（git 就是你的還原鍵）。
   - 有未提交變更或不在 git 裡 → 提醒使用者，並問「就地改」還是
     「另存 `<原檔名>-grilled.md`」。**沒問過不動未受版控的檔案。**
2. 掃出問題清單（先不問，自己先列）：
   - **模糊**：無法據以判斷對錯的敘述（「效能要好」「介面友善」）
   - **矛盾**：前後打架的兩段
   - **缺口**：該有卻沒有的（錯誤行為、邊界、驗收方式、範疇邊界）
   - **未定**：寫了「待討論」「TBD」的地方
3. 告訴使用者：「找到 N 個要談的點，我一題一題來」，並先問**範疇分級**
   （demo / mvp / full）——它決定後面追問的深度（見 grill.md 的表）。

## 拷問循環（一題一題，每題改一次文件）

對每個問題點：

1. **能自己查證的不問人**：答案可能在 codebase、其他文件、既有慣例裡
   ——先查，查到就直接寫進文件並告知「這條我從 X 查到，已補上」。
2. 真正需要決策的才問，**一次一題**，附上：
   - 這一條為什麼有問題（引用文件原文）
   - **你的建議答案**（讓使用者可以只回「好」）
   - 必要時 2-3 個選項與各自的後果
3. 使用者回覆後**立刻改文件**（Edit，不是最後一次性重寫）：
   - 改在原本那個段落裡，維持文件既有的結構與語氣
   - 使用者的用詞優先於你的用詞
   - 這樣中途離開也不會白談
4. 進下一題。前一題的答案若讓後面某題失效，直接說「這題因為剛才的
   決定已經沒有了」並跳過。

## 收尾

1. 文件末尾維護一個「未決事項」清單：使用者明確說「先不決定」的
   全部進這裡（含當時的選項），**不要假裝已經解決**。
2. scope 是 full 且文件屬於需求性質 → 提醒補「交接指紋」節
   （見 grill.md）。
3. 一段話總結：改了哪幾處、還剩幾條未決、建議下一步（通常是
   `/spec` 或 `/plan`）。

## 鐵則

- **只改文件，不碰程式碼。**要動程式碼是 /plan 之後的事。
- 不自行發明需求：文件沒有、使用者沒說的，一律問，不腦補。
- 不整份重寫。原文能留就留——使用者要的是他的文件變好，不是換一份。
- 使用者說「這樣就好」即停，剩下的進未決清單。
